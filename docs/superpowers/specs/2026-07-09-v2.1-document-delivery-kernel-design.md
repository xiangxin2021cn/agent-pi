# Agent Pi V2.1 Document Delivery Kernel Design

Status: implemented and regression-verified for the V2.1 release candidate on 2026-07-10.

## Objective

V2.1 turns the existing prompt-led document workflow into an application-owned delivery protocol for enterprise long documents, comprehensive data analysis, source-grounded conclusions, and strict template delivery.

The existing Goal Loop, selected-source boundary, knowledge base, document modes, and bounded sub-agent handoffs remain the foundation. V2.1 does not add another orchestration system.

## Product Boundary

V2.1 must improve four execution guarantees:

1. Every material user requirement has a stable ID and verification rule.
2. Long Markdown documents are written as recoverable section artifacts and assembled atomically.
3. Plan, audit, and merge transitions are application-validated rather than decorative labels.
4. Goal Audit evaluates the complete text artifact, not only its first preview block.

V2.1 does not implement a general recursive planner, a generic DAG platform, proprietary engineering-file parsers, or final Word/PDF pixel-perfect template cloning. Exact claim-to-locator graphs and strict OOXML rendering remain post-V2.1 work.

## Architecture

### 1. Requirement Ledger

`SessionTaskContract` owns a persisted `requirementLedger`. Each entry contains:

- stable ID;
- kind: deliverable, constraint, evidence, format, or verification;
- requirement text;
- verification method;
- source references;
- status: pending, satisfied, blocked, or failed.
- selected audit evidence references, verification time, and an explicit failure reason when verification does not pass.

The ledger is generated from deliverables, must-preserve constraints, evidence requirements, output formats, and acceptance criteria. Follow-up requests merge into the same ledger without renumbering existing entries.

The complete bounded ledger is included in execution and audit context. It is not truncated to the generic three-items-per-section display limit.

### 2. Transactional Document Artifact

A new session tool, `document_artifact`, owns long-form Markdown assembly. It supports:

- `init`: create a manifest with ordered required sections and final file name;
- `write_section`: atomically write or replace one section chunk;
- `status`: return manifest and section completion state;
- `prepare_merge`: verify every required section and freeze the exact section hashes;
- `assemble`: atomically assemble verified chunks into the formal output file;
- `validate`: verify the assembled artifact, section coverage, and non-empty content.

Artifacts are stored under the session data directory. Only the assembled file is written to the formal output directory. A failed section does not invalidate completed sections.

### 3. Executable Orchestration Transitions

Shared orchestration helpers validate transitions:

- plan -> audit when scoped tasks or section chunks are ready for review;
- audit -> plan for a bounded repair;
- audit -> merge only after the pre-merge artifact check passes;
- any active phase -> paused when user confirmation is required;
- merge -> done after final artifact validation.

Task dependencies are checked before a task becomes runnable. A merge request is rejected when required plan tasks, handoffs, or artifact sections are incomplete.

The first implementation enforces transitions through shared state helpers used by `SessionManager`. `document_artifact` owns artifact readiness and atomic assembly; Goal Audit owns the audit decision. General blocking of every legacy Write/Bash path is deferred until migration telemetry shows the tool is used reliably across Claude and Pi backends.

### 4. Complete-Text Goal Audit

Goal file verification separates UI preview from deterministic audit content:

- `preview` remains bounded for model and UI context;
- `auditContent` contains complete text for Markdown/TXT/JSON artifacts up to 5 MiB;
- files above 5 MiB fail closed into manual review rather than being accepted from a partial preview;
- deterministic structure, requirement, evidence-marker, visual, and template checks use `auditContent`;
- reviewer prompts continue to receive compact evidence, avoiding unbounded model context.

Office, PDF, and spreadsheet deep structural audit remains format-specific. Existing bounded conversions continue to run, but a truncated conversion cannot prove strict full-document compliance.

## Data Flow

1. User request enters `SessionTaskContract`.
2. The contract builds a stable requirement ledger and bounded task board.
3. Main or child agents produce scoped reports or document section chunks.
4. `document_artifact prepare_merge` validates required chunks and freezes their hashes.
5. `document_artifact assemble` writes the final Markdown atomically.
6. Goal Audit reads complete text through `auditContent`, checks the requirement ledger, and records an evidence package.
7. `SessionManager` validates audit, merge, repair, pause, and done transitions, then rewrites the evidence package with the final requirement statuses and completion-gate result. Failed work receives one bounded repair pass and unresolved work pauses for user review.

## Failure Handling

- Missing section: reject prepare/assemble and return exact section IDs.
- Empty or oversized section: reject only that section write.
- Interrupted assembly: keep the previous final file and temporary file cleanup state.
- Missing report handoff: keep the related task in needs-review.
- Oversized text artifact: manual review with explicit size evidence.
- Invalid phase transition: return current phase, allowed next phases, and blocking conditions.

## Verification

The implementation requires tests for:

- stable requirement IDs across follow-up merges;
- no ledger truncation in execution context;
- section write recovery and atomic assembly;
- rejection of missing required sections;
- plan/audit/merge transition validation;
- full-text detection of a missing requirement beyond the first 12 KB;
- fail-closed behavior for oversized text audits;
- existing selected-source, Goal Loop, template, and handoff regression suites.

The release candidate also passes full workspace TypeScript checks, Pi agent-server build validation, renderer orchestration view-model tests, transactional artifact tests, and requirement-provenance evidence-package tests.

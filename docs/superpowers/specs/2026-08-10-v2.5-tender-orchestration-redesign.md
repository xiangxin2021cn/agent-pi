## 1. 目标与非目标

### 1.1 目标

把投标工作台从「一点按钮就孵一窝子智能体」改成**可预期、可暂停、可验收**的四步流水线：

1. **项目资料登记** — 上传即登记，齐了就能进下一步  
2. **招标文件解析** — 每个上传文件产出可读 MD（一等成果）+ 结构化包  
3. **BOQ 五步法组价与资源汇总** — 强制对标 C5.1 工作底稿深度，联网尽调价格，汇总人材机消耗表  
4. **施工策划 → 进度 → 资源/现金流 → 正式递交稿** — 强制对标 N2-18 模版族，产出可导入 XML + 正式 DOCX/图表

聊天仍是命令面；**业务真相在项目目录与能力包**，不在对话里。

### 1.2 非目标（本版明确不做）

- 不做全自动「打开项目就跑完全流程」  
- 不做「打开阶段就打满并发」；第 2 步默认仅 2 并发，第 3 步默认串行，更高并发须显式调高  
- 不做图纸矢量识图算量（见 `docs/BIM_TAKEOFF_WORKBENCH_DESIGN.md`，独立工作台）  
- 不在本版重写全部 JSON schema 语义（只补宽容归一与门禁）  
- 不把 Goal Loop 伪监控 UI 当作流程真相

## 2. 问题诊断（为何必须重写编排）

| 失控模式 | 根因 | V2.5 对策 |
| --- | --- | --- |
| 第一步会话干到第三步组价 | Agent 工具面未按阶段裁剪；阶段与会话解绑 | 阶段工具白名单 + 一阶段一父会话 |
| 再点第二步又孵一堆子智能体 | 「进入阶段」= `openNewChat` + `start` 全量 dispatch | 进入 = resume 既有父会话；第 2 步最多维持 2 个在飞解析，靠 `advance` 补位 |
| 主会话卡住 | 子批 schema 失败 → 合并不过 → 父等门禁 | 宽容归一 + 失败批停派发不空转 + 人工「重试本批」 |
| 监控重启无效 | 监控是轮询 UI，不是控制室 | 真控制：停止派发 / 恢复 board / 重置本阶段编排 |
| 可读成果弱 | 过度崇拜 JSON pack，MD 被当成副产品 | **Human Artifact Gate**：无合格 MD 不能进下一阶段 |

## 3. 产品流程（四步）与过程成果

```text
[1 资料登记] ──人工确认齐套──▶ [2 招标文件解析]
                                      │ 每文件 MD + pack
                                      ▼
                              [3 BOQ 五步组价]
                                      │ 逐页工作底稿 + 资源消耗总表
                                      ▼
                              [4 策划·进度·成本·出稿]
                                      │ 策划MD → XML → 直方图/S曲线 → Work Plan DOCX
                                      ▼
                                   人工递交
```

阶段 ID（代码稳定，UI 文案可中文）：

| # | stageId | UI 名称 | 完成判据（人工可见） |
| --- | --- | --- | --- |
| 1 | `project-setup` | 项目资料登记 | 至少 1 个已登记文件；用户点「资料齐套，进入解析」 |
| 2 | `tender-document-analysis` | 招标文件解析 | 每个 registered 文件有**人审通过**的解析 MD；`document_analysis`/`boq_reconciliation` 就绪；`evaluation_strategy` 不强制 |
| 3 | `boq-five-step-pricing` | BOQ 逐页组价与资源汇总 | 定价范围内每项五步底稿验收 + `construction_resource_schedule` 汇总表 |
| 4 | `planning-and-submission` | 施工策划、进度、成本与出稿 | 见下方 3 个可见子步骤全部完成 |

**第 4 步 UI：一大阶段 + 三个可见子步骤**（底层仍一个 `stageId`）

| 可见子步骤 | 覆盖 | 完成探针 |
| --- | --- | --- |
| 4-A 施工策划 | 原 4a | `施工策划报告.md` 对人审通过 |
| 4-B 进度·资源·现金流 | 原 4b–4d | `tender-programme.msp.xml` + `tender-programme.p6.xml` + 人机直方图 + S 曲线 HTML |
| 4-C 正式出稿与核对 | 原 4e–4f | Work Plan DOCX + 轻量一致性审查 |

> V2.4 的独立 `submission` 阶段并入 4-C，避免再多一层易空转的门禁。旧 id `planning` / `submission` 通过别名映射。

## 4. 各阶段详细规格

### 4.1 第一步：项目资料登记（`project-setup`）

**用户动作**

1. 创建/打开投标项目，绑定工作目录  
2. 上传或选择招标文件（PDF/DOCX/XLSX 等）  
3. 系统写入登记表（documentId、路径、hash、kind 可后标）  
4. 用户点「资料齐套，进入解析」→ 阶段标记 `complete`

**过程成果**

- `tender-workspace` 源文件清单（registered）  
- 可选：用户标注 kind / 优先级（不强制才能进入第 2 步）

**明确不做**

- 不自动 spawn 任何子智能体  
- 不要求写分析 / 组价 / 策划  
- 主会话可选：仅用于「帮我建议文件 kind」，默认甚至可以无会话完成本步（纯 UI）

**门禁**

- `registeredCount >= 1`  
- 用户显式确认（按钮），不是模型自报完成

---

### 4.2 第二步：招标文件解析（`tender-document-analysis`）

**定位**

对**每一个已登记文件**做解析：归纳、结构化、写成**人可读 Markdown**。该 MD 是后续策划与合规的主阅读面；JSON 能力包是机器索引。

**默认执行模式：父会话 + 最多 2 并发解析**

```text
父会话（唯一）
  → 显示待解析队列
  → 启动/恢复后维持最多 2 个在飞子任务（maxConcurrency=2）
  → 某一份完成后自动 advance 补位下一份（dispatchEnabled 时）
  → 每份写出 MD → **人审查阅后勾选通过**（机器只做非空/结构探针）
  → 全部人审通过后运行时合成 document_analysis + 从 BOQ 源文件提炼 boq_reconciliation
```

**并发策略**

- 默认 `maxConcurrency = 2`；用户可降为 1（更稳）或显式调高（硬顶建议 3）  
- 子智能体禁止再 `spawn_session`；报告必须可合并  
- 「进入阶段」不得一次打满全部文件；只填满到并发上限

**每文件过程成果（强制）**

路径约定（项目内）：

```text
Agent Pi Outputs/<projectId>/document-analysis/
  <documentId>__<safeName>.md
  _index.md                          # 全册目录与交叉引用
packs/
  document-analysis.json
  boq-reconciliation.json            # 来自 BOQ 类文件的清单对账
```

单文件 MD 最低目录（可按 kind 裁剪章节）：

1. 文件身份（名称、版本、补遗关系）  
2. 一页纸摘要（给投标经理读）  
3. 关键约束（工期、罚款、强制出席、格式、TE/CPG 等）  
4. 与 BOQ / 规范 / 图纸的交叉引用  
5. 风险与待澄清问题  
6. 来源定位（页码/条款；允许归一后的 locator）

**合包规则**

- 运行时从已验收 MD + 子报告合成 `document_analysis`  
- `boq_reconciliation` 仅从 kind=`boq`（及补遗修订 BOQ）提炼真实支付行；拒绝汇总行/人造 composite  
- `evaluation_strategy` **不强制、不卡门禁**；若用户需要可另开增强任务生成，由人审阅，不自动视为阶段完成条件

**门禁**

- 每个 registered 文件：存在合格 MD（非空、含摘要节）且用户标记 `humanReview=accepted`  
- `sourceRefs` 字符串自动归一为 `{ documentId }`（warning，不整批作废）  
- 禁止本阶段调用组价/策划写包工具  
- 不要求 `evaluation_strategy` pack

---

### 4.3 第三步：BOQ 逐页组价与资源汇总（`boq-five-step-pricing`）

**定位**

按 BOQ **页/章（≈ COTO 章节）**逐项做 C5.1 级五步纯直接费推导；关键费率**必须联网尽调**；最后汇总项目级人材机消耗。

**强制知识绑定**

| 绑定键 | 用途 | 初始来源（需纳入产品知识库副本） |
| --- | --- | --- |
| `pricing.methodStandard` | 推导方法、深度、产出对标 | `C5.1_路床_单价推导.md`（现有样例路径见附录 A） |

运行时：阶段 brief / skill 注入该文件为 **唯一方法标准**；不允许用「通用资源库清单」替代五步工作底稿。

**五步清单（每 BOQ 支付项强制覆盖）**

| Step | 名称 | 最低产出 |
| --- | --- | --- |
| 1 | 范围与工程量 | 编码/描述/单位/数量原样；计量支付与规范条款；含/不含 |
| 2 | 方法与工效 | 工序、班组、设备、瓶颈公式；乐观/基准/悲观产量；`planningBasis.productionRate` |
| 3 | 资源消耗 | 人/机/料/分包/运输/损耗；每 BOQ 单位消耗与计算式 |
| 4 | 费率与纯直接费 | 单价来源、地点、日期、VAT 不含；**webEvidence**；项合价 |
| 5 | 复核与项风险 | 量价工效闭合；敏感性；未决证据 |

**联网尽调**

- 柴油、工资、设备租赁、水泥、骨料、沥青、主要分包等：必须 `web_search`/`web_fetch`（或等价）并写 `rateBasis.webEvidence[{url,accessedAt,note?}]`  
- 尽调地点默认取项目 `pricingLocation`（资料登记或解析阶段写入）；缺失则停步问用户  
- 无法核证 → `assumptionStatus: unverified`，不得编造

**默认执行模式**

```text
父会话
  → 展示 BOQ 页队列（来自 boq_reconciliation 真支付行）
  → 「组价下一页」串行（默认）
  → 每页产出：结构化 batch report + 可读 MD 工作底稿
  → 全部页验收后运行时 merge → boq_five_step_pricing
  → 运行时/主会话生成 construction_resource_schedule（人材机总表）
```

**新增一等成果：施工资源消耗总表**

能力包建议 id：`construction_resource_schedule`（或作为 `boq_five_step_pricing` 的强制附属 artifact）

字段级最低集：

- 资源类别：labour / plant / material / subcontract / transport / other  
- 品名、规格、单位  
- 总量（∑ 各项消耗 × BOQ 量）  
- 综合单价（尽调后主单价）与币种  
- 来源项列表（boqItemId[]）  
- 尽调证据或 unverified 标记  

可读输出：

```text
Agent Pi Outputs/<projectId>/boq-pricing/
  by-page/<sheetOrChapter>.md
  C5.1_style_workpapers_index.md
  施工资源消耗总表.md
  施工资源消耗总表.json
```

**门禁**

- 上游 `document_analysis` + `boq_reconciliation` 就绪  
- 定价范围内项 100% 五步验收（skipped 汇总行单独列表）  
- 资源总表生成且与项级消耗可勾稽  
- 关键费率 unverified 比例超过阈值 → 阶段可 `complete_with_review`，但不静默当事实

### 4.4 第四步：施工策划、进度、成本与出稿（`planning-and-submission`）

**输入（强制读取）**

1. 第 2 步全部解析 MD + 原文检索（selected sources，禁止扫盘）  
2. 第 3 步五步底稿、工效、资源总表  
3. 绑定模版族（附录 A）

**UI：一个大阶段，三个可见子步骤**（同一父会话、同一 `stageId`，子步骤状态写入 `stageRun.substeps`）

```text
4-A 施工策划
    └─ 4a 施工总策划（对标 N2-18 施工策划报告深度）
4-B 进度·资源·现金流
    ├─ 4b 详细进度排程 → MS Project XML + P6 XML（两者都出）
    ├─ 4c 人材机资源计划（直方图样式对标 Attachment 2/3）
    └─ 4d 现金流计划（对标 S-Curve HTML）
4-C 正式出稿与核对
    ├─ 4e 正式递交 Work Plan DOCX
    └─ 4f 一致性核对（轻量 audit）
```

用户在监控面板看到 4-A / 4-B / 4-C 进度条；「下一步」在子步骤内推进，子步骤未完成不得跳到下一可见步骤（可强制解锁需确认）。

#### 4a 施工总策划（可见步骤 4-A）

- **方法标准绑定**：`planning.methodologyDepthTemplate` → 安装包内 `N2-18施工策划报告_R05修订版.md`（项目可覆盖）  
- 必须吸收：招标工期/里程碑/罚则、项目特征、资源消耗与工效、施工逻辑顺序、交通疏导与关键构造物风险等（以当前项目解析为准，禁止整份照抄 N2）  
- 过程成果：`施工策划报告.md`（章节深度对标模版目录；缺章需显式 N/A 理由）  
- **人审通过**后才解锁 4-B

#### 4b 进度计划（可见步骤 4-B 之一）

- 以 4a 的大框架 + 第 3 步工效 + 分段资源为约束排详细作业  
- 过程成果：  
  - `programme.json`（内部 SoR）  
  - `tender-programme.msp.xml`（MS Project 可导入）  
  - `tender-programme.p6.xml`（Primavera P6 可导入）  
- **两份 XML 均为强制门禁**；CCS/Candy 作为后续扩展  
- 合同工期与关键里程碑必须可追溯到解析 MD 的条款定位

#### 4c 人材机资源计划（可见步骤 4-B 之二）

- 由 4b 活动 × 第 3 步资源消耗推月度/周度需求  
- 样式对标：  
  - Plant Histogram → Attachment 2 PDF  
  - Labour Histogram → Attachment 3 PDF  
- 过程成果：`plant-histogram.(html|pdf)`、`labour-histogram.(html|pdf)` + 数据表

#### 4d 现金流（可见步骤 4-B 之三）

- 模版绑定：安装包内 `S-Curve_Cash_Flow_Chart.html`（项目可覆盖）  
- 由进度 + 组价项金额（或资源成本）生成月度支出与累计 S 曲线  
- 过程成果：项目级 `S-Curve_Cash_Flow_Chart.html` + `cost_cashflow` pack  
- 4b–4d 齐套且探针通过 → 4-B 完成，解锁 4-C

#### 4e 正式递交 Work Plan（可见步骤 4-C 之一）

- 模版绑定：安装包内 `N2-18-Work_Plan_and_Proposed_Methodology.docx`（项目可覆盖）  
- 从 4a–4d 汇编英文（或招标要求语言）正式稿  
- 过程成果：`Work_Plan_and_Proposed_Methodology.docx`（+ 同源 MD）

#### 4f 核对（可见步骤 4-C 之二）

- 检查：工期数字、资源高峰、现金流合计、与 BOQ 项范围、双 XML 与策划一致性  
- 产出简短 `submission_audit.md`；阻断级问题禁止标记阶段完成  
- **人确认「可用于递交」或「仅内部稿」**后阶段 `complete`

**门禁**

- 4-A / 4-B / 4-C 各自产物齐全：两份进度 XML 均可解析、DOCX 可打开、HTML 含数据点  
- 模版绑定已解析且文件可读（先项目 bindings，缺省回落安装包）  
- 关键可读稿（策划 MD、Work Plan）以人审为主，机器只做存在性/结构探针

## 5. 编排控制面重写（核心）

### 5.1 控制原则

1. **一阶段一父会话**：`stageRun.parentSessionId` 稳定；再次「进入」= 聚焦并 resume，禁止默认新开父会话  
2. **按阶段默认并发**：第 2 步 `maxConcurrency=2`；第 3 步默认 `1`（串行按页）；第 4 步默认 `1`（按可见子步骤推进）  
3. **补位派发**：在飞数小于上限且 `dispatchEnabled` 时才 `advance`；禁止一次打满队列  
4. **子智能体禁止再 spawn**  
5. **阶段工具白名单**：第 1/2 步不可写 `boq_five_step_pricing` / planning packs  
6. **Human Artifact Gate**：规定的 MD/双 XML/DOCX 不存在，或关键稿未人审 → 阶段/子步骤不得 complete  
7. **监控 = 控制室**：停止派发、恢复失败项、重置本阶段编排（清 board/队列，不动已验收产物除非勾选「连产物一起清」）  
8. **侧栏只展示编排会话**：`taskBoard` / `stageRun` 关联；游离会话标「非编排」可归档

### 5.2 状态机（每阶段）

```text
idle → ready → running → waiting_user | blocked → complete
                 ↑__________________|
```

- `waiting_user`：下一份/下一页需点击，或费率地点未填  
- `blocked`：验收失败且已停止自动重试（不再空转 resume）  
- `complete`：仅门禁 + 用户确认（第 1 步）或产物探针（2–4 步）

### 5.3 Task Board 瘦身

保留：`batchId / brief / report / status / sessionId / error`  
删除或降级：打开项目时的隐式 `resume` 连锁；「恢复未完」不得跨阶段乱启第 3 步。

`start` 语义变更：

- 旧：把 failed 全改 pending 并尽量打满并发  
- 新：`start` = 绑定父会话 + 初始化队列；**不自动打满**  
- `advance`（新动作）= 仅派发队列下一项  
- `resume` = 仅重试 `failed` 且用户确认的项，或继续 `pending` 的下一项

### 5.4 监控面板（真控制）

| 按钮 | 行为 |
| --- | --- |
| 检查 | `status` only，对齐会话，不派发 |
| 下一步 | 调用 `advance`（推荐主按钮） |
| 恢复失败项 | 仅 failed → 重新 brief/spawn 一次 |
| 停止派发 | 置 `dispatchEnabled=false`，可选 abort 子会话 |
| 重置本阶段编排 | 清 board 与指针；可选保留已验收 MD |

顶部「监控中」仅表示轮询开启，**不得暗示业务在正确推进**。

## 附录 B — 与「普通会话」的体验对齐

用户可用普通会话写 MD；工作台必须做到：

- 同样可读（每步都有打开得到的文件）

若任一阶段做不到前两点，该阶段应降级为「打开普通会话 + 检查清单」，而不是假自动化。

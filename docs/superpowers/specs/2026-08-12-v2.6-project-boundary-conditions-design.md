## 0. 一句话结论

**是的，应当在「招标文件解析」与「BOQ 五步法组价」之间增加一道正式的「项目边界条件」阶段**——把项目所在地适用规范、计量标准、定额/工效库、市场价口径、投标人自有资源、组织策划大纲等，固化成可引用的能力包，再进入 BOQ 推导。  
V2.5 把「怎么跑」改对了；V2.6 要把「按哪套规矩跑」从隐含的南非公路默认，变成显式、可切换、可人工修订的项目级输入。

## 1. 尽调摘要（现状 vs 问题）

### 1.1 流水线骨架其实是通用的

当前权威阶段（`packages/server-core/src/tender-stage-run.ts`）：

| # | stageId | 门禁 required | 主产出 |
| --- | --- | --- | --- |
| 1 | `project-setup` | 无 | 资料登记 |
| 2 | `tender-document-analysis` | 无 | `document_analysis`（+ best-effort `boq_reconciliation`） |
| 3 | `boq-five-step-pricing` | **仅** `document_analysis` | `boq_five_step_pricing` + 资源总表 |
| 4 | `planning-and-submission` | `boq_five_step_pricing` | 策划/进度/成本/出稿 |

能力依赖图、软门禁、SoR/packs、Official Outputs、stage-deliverables 目录——**都不绑定国家**。  
问题不在「阶段机」，而在 **阶段机默认喂给 BOQ 的规矩全是 SANRAL 公路**。

### 1.2 南非公路耦合集中在「规矩层」

| 层 | 现状 | 可配置？ |
| --- | --- | --- |
| 知识包默认 | 仅 `knowledge/tender-sa-sanral/`（C5.1、N2-18 模版族） | 项目 `bindings.json` 可覆盖路径，但**没有第二套包可选** |
| `pricingStandard` | schema 字面量 `c51_pure_direct_cost_v1` | 否 |
| BOQ brief `qualityStandard` | 硬编码 `c51_pure_direct_cost_v1` + 9 条 C5.1 规则 | 否 |
| UI / dispatch 文案 | 「COTO 章节」「C5.1 纯直接费」「N2-18 深度」 | 否 |
| Skills | `tender-boq-five-step-pricing` / reconciliation / execution-planning 默认 SANRAL 口吻 | 可换 skill，但产品默认仍 SA |
| `TenderProject.jurisdiction` | 自由文本可选字段 | **运行时几乎不消费** |
| 费率模型 | `vatTreatment: 'exclusive'`、间接费排除在项直接费外 | 不适配中国综合单价等 |

### 1.3 用户真正缺的「第二步之后」

文档解析回答的是：**标书写了什么**。  
BOQ 五步法还需要：**我们按什么规矩、什么资源条件、什么组织意图去算**。

今天这层信息散落在：

- 人脑里（默认按南非公路做）
- C5.1 / N2 模版（深度样板，不是本项目边界）
- 联网询价（有，但是「边算边找」，缺少项目级基线）
- `bidder_commitments`（偏晚：在组价阶段之后才确认投入）

因此会出现：纳米比亚医院 / 中国公路 / 欧盟 FIDIC 项目仍被 COTO 章节话术与 C5.1 质检牵着走。

## 2. 目标与非目标

### 2.1 目标

1. 在解析完成之后、组价开始之前，强制形成一份 **项目边界条件包**（人可改、可引用、可进 Official Outputs）。
2. BOQ 子会话 brief **必须注入**该包：规范族、计量规则、工效/定额口径、市场价基线策略、自有资源、组织策划大纲。
3. 把 SANRAL/C5.1 降级为 **一个管辖区预设（profile）**，不再是唯一硬编码真理。
4. 用户可用 **自然语言一段话** 定义组织策划大纲；系统可从第 2 步解析结果 **建议**规范/计量/市场条件，但最终以人确认为准。
5. 保持 V2.5 控制面习惯：可暂停、可验收、软门禁（有可用结果可前进；缺边界则 **不能** 开 BOQ）。

### 2.2 非目标（V2.6 不做）

- 不一次做完全球所有定额库/工效库的完整内容生产（先做 **数据模型 + 注入 + 1～2 个预设**）。
- 不做 BIM 算量（独立设计稿）。
- 不把第 4 步策划模版族一次性多国化（可复用 bindings，本版优先服务 BOQ 前置）。
- 不自动替用户选定最终报价策略（仍是约束推导，不是替代商务决策）。
- 不在本版重写五步法数学内核为「中国综合单价引擎」——先允许 **pricingStandard 多态 + 策略接口**，首发仍保留 C5.1 实现，并加 **generic / draft** 标准。

## 3. 方案比选

### 方案 A — 独立新阶段（推荐）

```text
[1 资料登记] → [2 招标文件解析] → [2.5/3 项目边界条件] → [3/4 BOQ 五步组价] → [4/5 策划出稿]
```

| 优点 | 缺点 |
| --- | --- |
| 与用户心智一致：「解析后的边界输入」 | 阶段从 4→5，UI/alias/监控要改 |
| 门禁清晰：无边界包不能开 BOQ | 多一次人工确认点击 |
| 可单独「质检并整理」、可进 Official Outputs | 旧项目迁移要补默认包 |

### 方案 B — 第 2 步末端子步骤

解析阶段内增加「边界确认」子步骤。  
优点：少改 stageId；缺点：解析与决策边界混在同一阶段，监控/重试语义变脏，且「解析完成」与「可进组价」再次纠缠。

### 方案 C — 仅扩展 bindings / 项目创建表单

优点：改动小；缺点：用户往往要读完标书才知道适用规范；无法承载自然语言大纲与自有资源；不能成为 BOQ brief 的一等上游。

**推荐：方案 A。**  
阶段 ID 建议：`project-boundary-conditions`（UI：**项目边界条件**）。  
能力 ID 建议：`project_boundary`（packs/`project-boundary.json`）。

> 编号对外文案可仍称「第 3 步边界 / 第 4 步组价 / 第 5 步策划」，代码 stage 顺序插入即可；旧 `boq-five-step-pricing` 门禁改为要求 `document_analysis` **且** `project_boundary`。

## 4. 产品流程（V2.6）

```text
[1 资料登记]
      │
      ▼
[2 招标文件解析] ── 每文件 MD + document_analysis / boq_reconciliation
      │
      ▼
[3 项目边界条件] ── 人确认 / 可自然语言补全 / 可选管辖区预设
      │ 产出：project_boundary 包 + 可读 MD 纪要
      ▼
[4 BOQ 五步组价] ── brief 强制注入边界包；质量标准随 pricingStandard 切换
      │
      ▼
[5 策划·进度·成本·出稿]
```

### 4.1 第 3 步用户体验

进入阶段后，面板呈现一张 **边界工作表**（不是又开一窝子智能体；默认可 **单父会话协助填写**，可选「从解析自动建议」一次）：

1. **管辖区预设**（可选）：如 `sa-sanral-highway` / `generic-international` /（后续）`cn-highway-quota` …
2. **适用规范与合同框架**：从解析建议 + 用户勾选/改写（COTO、FIDIC Red、JTG、NEC…）
3. **计量标准**：CESMM / COTO measurement & payment / 中国清单计价规范 / 招标文件专用计量规则…
4. **定额 / 工效口径**：引用企业库、公开定额、或「以本项目解析+经验系数」；记录来源与置信度
5. **市场价策略**：地点、币种、VAT/税口径、询价必须联网的资源类别、不可核证时的标注纪律
6. **投标人自有资源**：自有设备/队伍/料场/营地能力；外租/分包边界
7. **组织策划大纲**：用户自然语言 1～N 段（必填软门禁：非空且 ≥ 某最小长度，如 80 字）

完成后：

- 写 `packs/project-boundary.json`
- 写可读 `Agent Pi Outputs/<parent>/project-boundary/项目边界条件.md`
- 更新 `bindings.json`（把本项目选中的 methodStandard / 知识包指向对应 preset）
- `capability-index` 标记 `project_boundary`
- 「下一步」才解锁 BOQ

### 4.2 与第 2 步解析的关系

| 来源 | 边界阶段如何用 |
| --- | --- |
| 解析 MD / `document_analysis` | 自动建议：业主、地点、合同形式、引用规范名、币种、工期 |
| `boq_reconciliation` | 提示清单计量体系线索（但不代替计量标准确认） |
| 用户自然语言 | 覆盖建议；写入 `organizationOutline` |
| 管辖区预设 | 填默认 `pricingStandard`、bindings、质检策略、文案模板 |

**纪律**：边界包引用解析成果用 sourceRefs；不得把 N2/C5.1 样板项目事实抄进本项目边界。

## 5. 数据模型（核心）

### 5.1 新能力 `project_boundary`

建议包结构（示意）：

```ts
interface TenderProjectBoundaryPack {
  schemaVersion: 1
  projectId: string
  profileId?: string              // e.g. 'sa-sanral-highway' | 'generic-international'
  jurisdiction: {
    countryCode?: string          // ISO 3166-1 alpha-2
    region?: string
    authority?: string            // SANRAL / 交通厅 / Employer
    currency: string              // ISO 4217
  }
  standards: {
    technicalSpecs: Array<{ id: string; title: string; version?: string; role: 'primary'|'secondary'|'reference' }>
    contractForm?: { id: string; title: string; version?: string }  // FIDIC / NEC / 国内示范文本…
    measurementStandard: { id: string; title: string; notes?: string }
  }
  pricing: {
    pricingStandard: string       // was literal c51… → open enum / string registry
    indirectCostPolicy: string
    taxRegime: { vatTreatment: string; notes?: string }
    ratePolicy: {
      location: string
      effectiveDateHint?: string
      mustVerifyOnline: string[]  // resource categories
      allowUnverifiedLabel: true
    }
  }
  productivity: {
    basis: 'enterprise_norms' | 'published_quota' | 'spec_derived' | 'user_provided' | 'mixed'
    notes?: string
    sources: Array<{ title: string; pathOrUrl?: string; confidence: 'high'|'medium'|'low' }>
  }
  bidderResources: {
    outline: string               // natural language or structured summary
    ownedPlant?: string[]
    ownedLabour?: string[]
    materialSources?: string[]
    subcontractBoundaries?: string
  }
  organizationOutline: {
    text: string                  // 用户自然语言主输入
    derivedAssumptions?: string[] // 系统提炼的可勾选假设
  }
  suggestedFromAnalysis?: {
    documentAnalysisPackPath?: string
    notes?: string[]
  }
  humanConfirmedAt?: string
  readiness: 'draft' | 'ready' | 'needs_review'
}
```

### 5.2 阶段与门禁变更

```ts
// STAGES (conceptual)
project-setup
tender-document-analysis     // produces document_analysis, boq_reconciliation
project-boundary-conditions  // requires document_analysis; produces project_boundary
boq-five-step-pricing        // requires document_analysis + project_boundary
planning-and-submission      // requires boq_five_step_pricing
```

`STATIC_DEPENDENCIES`：

- `project_boundary`: `['core', 'document_analysis']`
- `boq_five_step_pricing`: 增加依赖 `project_boundary`
- `execution_plan` 等策划能力：建议 **读取** 边界包中的 `organizationOutline`（本版可 soft-require）

`STAGE_WRITE_ALLOWLIST`：仅边界阶段可写 `project_boundary`。

### 5.3 Soft gate

与 V2.5.2 一致：**有可用内容即可推进**，不因字段仪式卡死。

进入 BOQ 的最低可用条件建议：

- `organizationOutline.text` 非空且达最小长度
- `standards.measurementStandard` 有 title 或 id
- `pricing.pricingStandard` 已选定（可从 profile 默认）
- `jurisdiction.currency` 已定
- pack readiness ∈ `ready | needs_review | not_ready(但非空)` 均可进，但 UI 警告缺项

### 5.4 注入 BOQ brief

扩展 `TenderBoqBatchBrief`：

- `projectBoundary`：包摘要或路径 + 关键字段内联
- `methodStandard`：由边界阶段写回的 bindings 解析
- `qualityStandard.id`：来自 `pricing.pricingStandard`，不再写死 `c51_…`

`upstreamDeliverables`：加入边界阶段 catalog 中 citable 项。

## 9A. 专业报告质量（V2.6 并行目标）

### 问题（实测）

R573 解析稿参差：好的 HSE 稿已有合规要点，但仍大量「文件 / 文档 ID / 来源路径 / Sheet 数量 / 分析说明」元信息；弱稿更像「读文件说明书」，不像投标工程师给商务/技术经理看的纪要。  
根因：

- child brief `objective` 只要求 “readable Markdown”，未规定**读者角色与行业体裁**
- skill 模板偏 identity / source locators，鼓励文件中心叙述
- 合并 summary（`tender-document-analysis-md.ts`）甚至解释 pack 路径，对客户无价值
- 未先判定 **项目业态**（公路 / 房建 / 医院 / 电力…），无法切换行话与章节骨架

### 目标

可读报告必须像**该行业投标作业纪要**，不是系统日志。

| 规则 | 要求 |
| --- | --- |
| 读者 | 投标经理 / 造价 / 技术负责人（不是开发者） |
| 业态判定 | 从登记资料 + 标题/业主/清单结构推断 `projectIndustry`（可写入边界包，解析阶段先推断草稿） |
| 行话 | 公路：桩号、保通、路床、导改、P&G…；房建：分部工程、措施费…；按业态词表，禁止空泛「本文件讲述了…」 |
| 禁写/少写 | 内部 documentId、绝对路径、Agent Pi Outputs、batchId、「分析范围仅限本文件」套话堆砌 |
| 应写 | 对报价/工期/合规/风险的约束；必须澄清项；与 BOQ/规范交叉的硬条件；交付物与配备刚性要求 |
| 出处 | 条款/页码用脚注或括号短引，不把「文件元数据」当正文主角 |
| 体裁 | 按文档角色切换骨架：HSE 规范 ≠ BOQ ≠ 岩土报告 ≠ 环境授权 |

### 落地手段

1. **`projectIndustry` + `documentRole` 推断**（解析 child brief 注入；边界阶段可修订）  
2. 重写 `tender-document-parsing` skill + document batch `objective`：专业体裁 checklist

## 9B. 运行稳定性热修（优先）

### 现象

用户反馈运行中**自动退出 / 不稳定**。生产 `main.log` 默认关闭；真相在 `~/.agent-pi/logs/stability.log`。

### 已定位根因（2026-08-12）

```
RangeError: Invalid string length
  at PiEventAdapter.accumulateOutput (.../base-event-adapter.ts)
  at PiEventAdapter.adaptEvent
  at _PiAgent.handleSubprocessEvent
```

- 工具流式输出用 `current + delta` **无上限拼接**（`packages/shared/src/agent/backend/base-event-adapter.ts`）  
- 大 PDF/OCR/Excel 工具输出可达数百 MB → 触及 V8 字符串上限 → **uncaught exception 风暴**（日志中单次会话可达数百条）  
- 同期主进程 RSS 可爬到 **~1.1 GiB+**（memory peak），加剧卡顿/假死体感  
- spawn 内存门禁只挡新 spawn，**挡不住已在飞工具输出撑爆字符串**

### 热修要求（可先发 2.5.3，再并进 2.6）

1. `accumulateOutput`：设硬上限（如 2–8 MiB）；超出截断并标记 `truncated`；**禁止抛崩主进程**  
2. uncaught 路径：同类 RangeError 记稳定性日志后继续，避免连环刷屏  
3. 大工具结果落盘引用（path + preview），UI/会话只保留摘要  
4. 投标默认并发在内存高压时自动降到 1–2（已有 guard 可联动）  
5. Overview/状态轮询保持 V2.5.2 节流，避免雪上加霜  

### 成功标准（稳定性）

- 大文件解析不再因 `Invalid string length` 拖垮主进程  
- stability.log 无同错秒级风暴  
- 长跑 RSS 有回落，不单调涨到 OOM

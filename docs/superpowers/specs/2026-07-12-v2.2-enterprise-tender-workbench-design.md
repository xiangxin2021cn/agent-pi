# Agent Pi V2.2 Enterprise Tender Workbench Design

Status: Approved direction, implementation scope locked for the first V2.2 vertical slice.

## 1. Objective

V2.2 begins the transition from a document-oriented agent workbench to an enterprise project workbench. The first vertical is construction tender intelligence because tender requirements, evaluation criteria, BOQ scope, programme, resources, cost, cash flow, and formal submissions all depend on the same source-controlled project facts.

The first release slice is **Tender Intelligence Core**. It does not attempt to implement every downstream calculation engine. It establishes the durable business model and deterministic gates that those engines will consume.

## 2. Product Principle

Chat is the command and explanation surface. It is not the business system of record.

The system of record is a project-local, versioned Tender Workspace containing:

- source documents and addenda;
- mandatory, qualification, technical, contractual, pricing, deadline, format, and evaluated requirements;
- pass/fail, threshold, and weighted evaluation criteria;
- required deliverables and submission formats;
- planned responses that connect requirements and criteria to deliverables and evidence;
- deterministic readiness audit results.

The model remains inspectable JSON in V2.2. A relational or vector database is explicitly deferred until the workflow and entity boundaries are proven.

## 3. Architectural Fit

V2.2 extends the existing application-owned control plane:

- `SessionManager` remains the turn and lifecycle boundary.
- Goal Loop remains responsible for accepting or rejecting completion.
- selected-source hard boundaries remain authoritative;
- MinerU extraction manifests provide page, block, and bounding-box evidence;
- transactional document artifacts remain responsible for long Markdown delivery;
- Project Memory Lite remains compact and project-scoped;
- skills describe professional workflow, but deterministic tools own persistent business state and validation.

V2.2 must not add tender-specific branching directly into the large Goal Controller. Domain checks are exposed through a small, pure business-core package and a session tool adapter.

## 4. Canonical Business Model

### 4.1 Project

The project record identifies the tender reference, title, employer, currency, closing time, jurisdiction, and lifecycle status.

### 4.2 Source Document

Every source document has a stable ID, kind, path, revision metadata, status, and optional supersession links. Supported kinds include notice, tender data, contract data, scope, specification, drawing, BOQ, returnable schedule, addendum, template, and supporting evidence.

No requirement may cite an unregistered document.

### 4.3 Source Locator

A locator can contain:

- document ID;
- page or sheet;
- clause or section;
- cell or range;
- MinerU block ID;
- bounding box;
- short exact excerpt.

Locators preserve source precision without copying entire licensed documents into the business model.

### 4.4 Requirement

Requirement classifications are explicit:

- `mandatory`
- `qualification`
- `technical`
- `contractual`
- `pricing`
- `deadline`
- `format`
- `evaluated`

Each requirement records its source locator, criticality, required evidence, owner, status, and optional affected entities.

### 4.5 Evaluation Criterion

Evaluation criteria distinguish:

- `pass_fail`
- `threshold`
- `weighted`

They record weight, minimum score, linked requirements, source locator, evidence expectations, and response status. Weight is data, not prose.

### 4.6 Deliverable

Deliverables record title, format, submission section, due time, template path, linked requirements, and status. A mandatory requirement is not covered merely because it appears in narrative; it must map to a deliverable or an explicitly accepted non-document response.

### 4.7 Response Plan

A response plan links requirements and criteria to:

- one deliverable;
- one response section;
- evidence locators or evidence artifact paths;
- an owner;
- a lifecycle status.

Unverified assumptions are recorded as gaps and may not become unconditional core conclusions.

## 5. Deterministic Audits

The first readiness audit reports, without model judgment:

1. structural schema validity;
2. duplicate or broken entity references;
3. requirements citing missing or superseded documents;
4. mandatory requirements without response coverage;
5. evaluation criteria without response coverage;
6. weighted score coverage;
7. deliverables without linked requirements;
8. verified responses without evidence;
9. unresolved blocked requirements and response plans;
10. submission readiness status.

Readiness states are:

- `not_ready`: structural errors, uncovered mandatory requirements, or blocked critical items;
- `needs_review`: structurally valid but evidence or verification is incomplete;
- `ready`: all mandatory requirements and criteria are covered, required deliverables exist in the model, and verified responses carry evidence.

The audit does not claim that a bid will win or that a human tender manager has approved it.

## 6. Project-Local Persistence

Tender Workspace data is stored under the selected physical working directory:

```text
<working-directory>/.agent-pi/business/tender/<project-id>/
  tender-workspace.json
  readiness-audit.json
```

Rules:

- IDs are filesystem-safe and stable.
- Writes are atomic.
- A workspace cannot escape the selected working directory.
- Source files are referenced, never moved or deleted.
- The tool does not scan the working directory for sources.
- Addenda and revisions are explicit user/agent registrations.
- Model updates reject invalid cross-references instead of persisting partial corruption.

## 7. Session Tool

The `tender_workspace` session tool owns project-local business state.

Initial actions:

- `init`
- `upsert_documents`
- `upsert_requirements`
- `upsert_criteria`
- `upsert_deliverables`
- `upsert_responses`
- `status`
- `validate`

Mutating actions require execution mode. The returned payload always includes the model path, audit path, revision, and readiness summary.

## 8. Tender Intelligence Core Skill

The skill is intentionally smaller than the existing all-in-one SANRAL workflow. It defines this bounded sequence:

1. confirm selected source set;
2. register source documents and revisions;
3. extract requirements and criteria with exact locators;
4. separate pass/fail, threshold, weighted, and contractual obligations;
5. register deliverables and response plans;
6. run deterministic readiness audit;
7. pause for user confirmation when source scope, precedence, or interpretation is ambiguous;
8. only then hand downstream work to BOQ, methodology, schedule, resource, cost, or cash-flow capabilities.

Rates, productivity benchmarks, and full copyrighted standards must not be embedded in the skill.

## 9. V2.2 Capability-Pack Roadmap

Tender Intelligence Core is the dependency for the following separately testable packs:

1. Evaluation Strategy
2. BOQ-Specification-Drawing Reconciliation
3. Construction Methodology and Project Execution Planning
4. Integrated Schedule and Resource Planning
5. Cost and Cash-Flow Planning
6. Submission Assembly and Red-Team Audit
7. Post-award Project Controls

Every pack consumes stable Tender Workspace IDs instead of re-reading the whole conversation.

## 10. UI Direction

The enterprise UI will be an operational register, not a marketing dashboard. The planned project workspace uses dense editable tabs:

- Sources
- Compliance
- Evaluation
- Deliverables
- BOQ
- WBS and Programme
- Resources
- Cost and Cash Flow
- Risks and Decisions

The V2.2 first slice may expose Tender Workspace status through tool results and the existing file preview. A dedicated register UI follows after the model and audit behavior are proven by fixtures.

## 11. Completion Gates

The first slice is complete when:

- a user-selected project directory can initialize a Tender Workspace;
- registered documents, requirements, criteria, deliverables, and responses survive restart as valid JSON;
- invalid entity references cannot be persisted;
- an addendum can supersede a prior source and the audit identifies stale citations;
- uncovered mandatory requirements and zero criterion coverage cannot report ready;
- verified responses without evidence cannot report ready;
- the Skill directs the agent through the tool and selected sources without scanning the working directory;
- tests pass in `business-core`, `session-tools-core`, Shared, Server Core, and Electron type checks.

## 12. Non-Goals

- No automatic bid/no-bid decision.
- No claim of legal, contractual, engineering, or commercial approval.
- No automatic pricing from hard-coded rates.
- No complete CPM, resource leveling, or cash-flow engine in the first slice.
- No recursive sub-agent hierarchy.
- No implicit working-directory scan.
- No bundling of licensed FIDIC, COTO, AACE, PMI, or other protected standards.

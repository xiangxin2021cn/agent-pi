# Agent Pi V2.2 Tender Completion Master Plan

> Execute in order. Each phase is independently testable and must be committed before the next phase.

**Goal:** Complete the six remaining Tender Intelligence capability packs on top of the proven Tender
Workspace core, without mixing project implementation or investment business state into the tender
plugin.

**Architecture:** Keep `tender-workspace.json` as the stable source/requirement/criterion/deliverable
core. Store capability data in separate versioned envelopes under `packs/`, maintain a deterministic
capability index, and expose one typed `tender_capability` session tool. Model output may propose
records; business-core parsers and audits decide what can be persisted or declared ready.

**Technology:** TypeScript, Valibot, Bun tests, existing session-tools adapters, existing shared Skill
loader, existing Electron RPC and file-preview components.

## 1. Locked Scope and Success Criteria

This plan implements only:

1. Evaluation Strategy;
2. BOQ-Specification-Drawing Reconciliation;
3. Construction Methodology and Execution Planning;
4. Integrated Schedule and Resource Planning;
5. Cost and Cash-Flow Planning;
6. Submission Assembly and Red-Team Audit.

Project Delivery Controls and Resource Investment Intelligence are separate later plugins. The
knowledge exchange contract is defined in
`docs/V2.2_ENTERPRISE_PLUGIN_BOUNDARIES_AND_KNOWLEDGE_EXCHANGE.md`; it is not a reason to couple their
stores to Tender Workspace.

V2.2 tender completion is accepted when:

- all six packs have versioned schemas, pure audits, fixtures, and session-tool persistence;
- pack dependencies and stale revisions are deterministic;
- no pack scans the working directory or reconstructs business state from chat;
- no rate, productivity, quantity, source precedence, or compliance conclusion is persisted without
  source or explicit assumption status;
- formal submission readiness requires the core and every required pack to pass;
- the Tender UI reads typed RPC data rather than raw JSON;
- all package tests and `bun run typecheck:all` pass.

```ts
export type TenderCapabilityId =
  | 'evaluation_strategy'
  | 'boq_reconciliation'
  | 'execution_plan'
  | 'schedule_resources'
  | 'cost_cashflow'
  | 'submission_audit';

export interface TenderCapabilityRevisionRef {
  capability: TenderCapabilityId | 'core';
  revision: number;
}

export interface TenderCapabilityEnvelope<T> {
  schemaVersion: 1;
  capability: TenderCapabilityId;
  projectId: string;
  revision: number;
  coreRevision: number;
  upstream: TenderCapabilityRevisionRef[];
  updatedAt: string;
  data: T;
}

export interface TenderCapabilityIndexEntry {
  capability: TenderCapabilityId;
  enabled: boolean;
  required: boolean;
  revision: number;
  readiness: 'not_ready' | 'needs_review' | 'ready';
  issueCount: number;
  stale: boolean;
  updatedAt: string;
}
```

Registry rules:

- `evaluation_strategy` depends on `core`;
- `boq_reconciliation` depends on `core`;
- `execution_plan` depends on `core`, `evaluation_strategy`, and `boq_reconciliation`;
- `schedule_resources` depends on `core` and `execution_plan`;
- `cost_cashflow` depends on `core`, `boq_reconciliation`, and `schedule_resources`;
- `submission_audit` depends on `core` and every enabled pack;
- a project explicitly configures which packs are enabled and which enabled packs are required;
- an envelope is stale when its stored core or upstream revision no longer matches;
- a stale pack cannot report `ready`.

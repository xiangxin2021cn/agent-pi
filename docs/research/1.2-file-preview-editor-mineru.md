# Agent Pi V1.2 Research: Unified File Preview, AI Selection Editing, MinerU Extraction, AnySearch Setup

Date: 2026-07-02

## Scope

V1.2 should focus on improving the agent's ability to produce expected artifacts and correct document work in place. This research covers four product directions:

1. Unify every file preview entry point so Markdown editing and MD/PDF/DOCX export are available consistently wherever a preview is opened.
2. Add selection-based AI rewrite in Markdown edit mode, using the same session intelligence and project memory as the normal conversation flow.
3. Integrate MinerU as an optional extraction provider for PDF/image documents, with reusable extraction artifacts and citation-grade project memory.
4. Ship first-run credential and search setup so MinerU and AnySearch MCP can be enabled without manual environment editing.

The goal is not to replace existing flows. The implementation should be additive: when a feature is disabled or unavailable, current V1.1.3 behavior must remain intact.

## Current Branch Status

Implemented in `codex/V1.2` so far:

- Markdown/office-derived Markdown previews expose consistent Markdown download and PDF/DOCX export actions.
- Editable Markdown previews support right-click selected text, an anchored AI instruction box, hidden-session rewrite, Original/Proposed preview, and explicit Apply before replacement back into the selected range.
- Selection rewrite uses the normal session send path, inherits the active working directory, and therefore keeps the existing project-memory injection path.
- MinerU precision extraction is workspace opt-in only. The token dialog links to https://mineru.net/apiManage/token, stores tokens in the secure credential store, and does not enable extraction just because a token exists.
- PDF attachment storage can call MinerU only when workspace MinerU extraction is explicitly enabled and a token is available, then reuses the generated Markdown through `markdownPath` and records a first-pass `extractionManifestPath`.
- Successful MinerU extraction now records compact Project Memory Lite source, citation, fact, and prompt-context entries linking the original PDF, generated Markdown, optional raw JSON sidecar, extraction manifest, cleanup audit sidecar, and first-pass page/block citation records.
- When the workspace scan-noise option is explicitly enabled, MinerU Markdown runs through conservative repeated-line cleanup and writes a `.mineru.cleanup.json` audit file.
- MinerU raw JSON citation extraction now handles multiple observed layout schema variants, including `pages`, `pdf_info`, `para_blocks`, `layout_dets`, alternate text/type/page keys, bbox objects, and polygon coordinates.
- Claude/Pi attachment prompts now expose both `[Markdown version: ...]` and `[Extraction manifest: ...]` when MinerU produces sidecars.
- The Electron `beforePack` hook stages MinerU Open API `0.5.9` platform binaries into `resources/bin/<platform-arch>/`, and runtime command resolution prefers bundled resources before falling back to system `mineru-open-api`.
- AnySearch MCP is available as a recommended source template but is installed disabled and unauthenticated. Loading it opens an API key dialog with https://www.anysearch.com/docs#search-api.
- Folder attachment selection now creates a path-only reference attachment with the local absolute folder path; it does not recursively upload the folder contents.
- Stored attachment clicks now propagate `markdownPath` / `extractionManifestPath` into the unified preview router. PDF and spreadsheet overlays keep their native previews but show MD/PDF/DOCX actions when a Markdown sidecar exists; Office previews reuse generated Markdown sidecars when available and can export provided preview content.

Still open for later V1.2 work:

- More advanced image-level watermark/signature cleanup and production validation against additional MinerU JSON samples.

- `packages/server-core/src/project-memory-lite.ts` already stores source evidence in `.agent-pi/brain/sources/sources.jsonl` and links in `.agent-pi/brain/citations.jsonl`.
- Current branch now adds first-pass page/block extraction provenance from MinerU raw JSON sidecars. It still needs hardening against MinerU version-specific layout schema changes.
- Existing design notes explicitly leave scanned/binary preview checks and citation-level checks as future work. MinerU fits that gap.

### AnySearch MCP Capability

Official sources checked:

- AnySearch docs: https://www.anysearch.com/docs
- AnySearch MCP server: https://github.com/anysearch-ai/anysearch-mcp-server
- AnySearch API key console: https://anysearch.com/console/api-keys

Verified points:

- AnySearch exposes a unified search API with base URL `https://api.anysearch.com`.
- AnySearch MCP Server supports general web search, vertical domain search, parallel batch search, and full-page URL extraction.
- The MCP endpoint is `https://api.anysearch.com/mcp`.
- Streamable HTTP is natively supported and is the recommended no-proxy transport when the client supports it.

Implication: AnySearch MCP is viable as an optional search foundation if V1.2 adds a first-run credential prompt and a clean fallback path.

## Direction 1: Unified File Preview And Export

### Problem

The user-visible expectation is simple: any place that opens a file preview should expose the same high-value actions when possible:

- preview,
- edit when safe,
- save,
- export Markdown,
- export PDF,
- export DOCX,
- reveal/open externally.

The current system has the foundation but the capability is distributed by overlay type. That creates inconsistent behavior depending on whether the user clicks a chat file link, a response-card file path, a right-sidebar output file, or a legacy file viewer.

### Proposed Architecture

Introduce a single preview capability model:

```ts
interface FilePreviewCapability {
  filePath: string
  previewType: 'markdown' | 'pdf' | 'spreadsheet' | 'office' | 'code' | 'text' | 'json' | 'image'
  editable: boolean
  canSave: boolean
  canDownloadMarkdown: boolean
  canExportPdf: boolean
  canExportDocx: boolean
  derivedMarkdownPath?: string
  originalPath?: string
}
```

Then make every file preview entry point call the same `onOpenFile(path)` or a future `openFilePreview({ path, source })`.

Capability rules:

- Native `.md` / `.markdown`: editable, saveable, downloadable, exportable to PDF/DOCX.
- Office files with generated Markdown preview: read-only original preview, with "Open Markdown version" and export actions against the Markdown derivative.
- PDF with MinerU/other extracted Markdown: PDF preview remains primary, with "Open extracted Markdown" and export actions against the derivative.
- Spreadsheet with generated Markdown/table preview: preview table remains primary, with Markdown derivative export when available.
- Code/text/JSON/image: keep preview/open/reveal; do not fake document export unless a Markdown derivative exists.

### Implementation Plan

1. Audit entry points
   - Search and remove any direct `window.electronAPI.openFile(...)` calls used for files that can be previewed.
   - Keep direct external open for directories and unsupported binaries.
   - Replace remaining `FileViewer` usages with the unified overlay or delete only if unused.

2. Add derived Markdown awareness
   - Extend preview state with `derivedMarkdownPath?: string`.
   - Add an RPC helper to find known sidecar Markdown for a file, initially:
     - `storedAttachment.markdownPath`,
     - MinerU extraction manifest,
     - same-folder generated `.md` sidecar where explicitly registered.

3. Normalize header actions
   - Move action calculation out of `DocumentFormattedMarkdownOverlay` into a shared helper.
   - Reuse the same button semantics in PDF/spreadsheet/office overlays.
   - Do not show disabled export buttons when no Markdown content exists.
   - Current branch has shipped the first slice: stored attachment sidecars are propagated to preview state, PDF/spreadsheet overlays render shared sidecar actions, and Office previews use sidecar Markdown when present.

4. Tests
   - Unit test capability calculation for `.md`, `.pdf` with sidecar, `.docx` with sidecar, `.xlsx`, image.
   - Renderer test that right-sidebar file click and Markdown file link produce the same preview action set.
   - Export smoke test for MD/PDF/DOCX remains under existing `files.preview-export.test.ts`.

## Direction 2: AI Rewrite For Selected Text In Edit Mode

### Problem

The app already supports reviewing Markdown artifacts, but editing still requires manual rewrite. The desired workflow is:

1. Open an output Markdown file.
2. Enter edit mode.
3. Select a paragraph or section.
4. Right-click and ask the agent to revise it.
5. The agent uses project memory and normal session context.
6. Replacement is written back to the selected location.

This is feasible because the app already has both halves:

- `TiptapMarkdownEditor` exposes an editor instance with selection state.
- Chat response cards already implement selection-driven follow-up UI and annotation flows.

### Proposed UX

In Markdown edit mode, selected text should show a compact AI edit menu:

- "Rewrite selection"
- "Improve clarity"
- "Shorten"
- "Make more formal"
- "Custom instruction..."

For custom instructions, open a small prompt box anchored near the selection. The replacement should not be blindly committed. The default flow should be:

1. Generate replacement.
2. Show inline diff or preview.
3. User applies or rejects.
4. On apply, replace selection and mark document dirty.
5. User can save with the existing Save button.

This preserves user control and avoids accidental destructive edits.

### Backend Strategy

Use the existing session intelligence instead of a standalone "rewrite API" with weak context.

Recommended request shape:

```ts
interface SelectionRewriteRequest {
  sessionId: string
  filePath: string
  sourceMtimeMs?: number
  selectedMarkdown: string
  surroundingMarkdown: string
  instruction: string
  mode: 'replace-selection'
}
```

The server should run a bounded rewrite turn using the same session context builder used for normal messages, including:

- working directory,
- project memory context,
- enabled sources/skills where applicable,
- task contract/document plan when present,
- selected text and surrounding context.

The model response should be constrained to a replacement payload:

```json
{
  "replacementMarkdown": "...",
  "notes": "optional short explanation"
}
```

### Safety Checks

- Before applying, compare the selected text hash with the current selection content.
- Before saving, keep the existing mtime check already used by Markdown file editing.
- Reject replacement if it is empty unless the user explicitly requested deletion.
- Preserve undo history through Tiptap transactions.
- Do not auto-send the whole file to the model. Send the selection, a bounded surrounding window, and retrieved project memory.

### Tests

- Editor unit test: selected range is captured and replaced.
- RPC test: selection rewrite prompt includes file path, selected text, surrounding text, and project memory marker.
- Conflict test: replacement fails if the file changed on disk or the selected range changed.
- Manual test: open a generated `.review.md`, select a paragraph, rewrite it, save, export PDF/DOCX.

## Direction 3: MinerU Extraction For PDF And Scanned Documents

### Problem

The current attachment flow can reuse Office Markdown conversions but not PDF extraction. That means scanned PDFs and layout-heavy tender documents are weak inputs unless the model/provider can read the PDF directly. It also limits source citation precision.

MinerU can improve this by producing:

- normalized Markdown for agent reading,
- structured JSON/layout for citations,
- optional DOCX/HTML outputs for preview/export,
- OCR/table/formula handling for complex documents.

### Proposed Extraction Provider Interface

Add a provider layer instead of hard-coding MinerU into attachment storage:

```ts
interface DocumentExtractionProvider {
  id: 'mineru' | 'markitdown' | 'pdf-text'
  canExtract(input: ExtractionInput): Promise<boolean>
  extract(input: ExtractionInput, options: ExtractionOptions): Promise<ExtractionResult>
}

interface ExtractionResult {
  markdownPath?: string
  jsonPath?: string
  htmlPath?: string
  docxPath?: string
  manifestPath: string
  citationIndexPath?: string
  warnings: string[]
}
```

Initial routing:

- PDF/image and MinerU enabled: MinerU first.
- Office/spreadsheet: keep existing MarkItDown/table flow, later wrap it under the provider interface.
- MinerU unavailable/fails: keep original file only and current behavior.

### Storage Layout

Store extraction artifacts under the session data or attachment folder:

```text
attachments/
  <id>_original.pdf
  extraction/
    manifest.json
    content.md
    layout.json
    citations.jsonl
```

Manifest example:

```json
{
  "provider": "mineru",
  "providerVersion": "v0.5.9",
  "sourcePath": "...",
  "sourceSha256": "...",
  "markdownPath": ".../content.md",
  "jsonPath": ".../layout.json",
  "createdAt": 1782979200000,
  "options": {
    "ocr": true,
    "table": true,
    "formula": true,
    "model": "pipeline"
  }
}
```

Extend attachment metadata:

```ts
interface StoredAttachment {
  markdownPath?: string
  extractionManifestPath?: string
  citationIndexPath?: string
}
```

This is backward compatible because the new fields are optional.

### Prompt Reuse

The current agent prompt already includes:

```text
[Markdown version: <path>]
```

So V1.2 should set `markdownPath` for MinerU-extracted PDFs. That immediately lets Claude/Pi/Codex-style agents read the extracted text from disk instead of relying only on inline PDF handling.

For Pi, this is especially important because current PDF handling is path-only. A MinerU Markdown sidecar gives weaker/local models a much better text input.

### Citation Index

MinerU JSON is transformed into compact citation records. The current adapter supports common `pages`/`pdf_info` layout variants, page index/number aliases, block type aliases, direct bbox arrays, bbox objects, and polygon coordinates. The app-side normalized shape stays stable:

```json
{
  "sourcePath": ".../original.pdf",
  "markdownPath": ".../content.md",
  "page": 12,
  "blockId": "p12-b034",
  "type": "paragraph",
  "textHash": "sha256:...",
  "textPreview": "first 160 chars...",
  "bbox": [72, 120, 530, 180]
}
```

Project Memory Lite should store only compact references:

- `sources/sources.jsonl`: source file and extraction manifest.
- `citations.jsonl`: links from source page/block to goal audit or output artifact.
- `facts.jsonl`: concise verified facts only after audit/review confirms them.

Do not store full OCR text in `entries.jsonl`.

### Signature And Watermark Cleanup

The safe default is non-destructive:

- Never modify the original PDF.
- Cleanup affects only extraction derivatives.
- Watermarks can be suppressed when they are repeated, low-content overlays across many pages.
- Signatures, stamps, seals, and handwritten marks should be preserved as visual evidence or tagged as non-body content. They should not be blindly removed.

V1.2 can ship a conservative first slice:

- Detect repeated watermark-like OCR fragments and exclude them from body Markdown.
- Keep a `suppressed_blocks.jsonl` audit trail.
- Add a setting: "clean repeated scan noise/watermark text".
- Leave signature classification as metadata unless the user explicitly asks to ignore signatures.

### Configuration

Suggested settings:

- Enable MinerU extraction: off by default. The app may detect bundled/system `mineru-open-api`, but precision extraction starts only after the user explicitly enables MinerU for the workspace or upload flow.
- MinerU command path: prefer bundled `mineru-open-api`; fallback to system `mineru-open-api`.
- Token/API config: read from app secure credential storage first, then `MINERU_TOKEN`, then `~/.mineru/config.yaml`.
- Default model: `pipeline` for lower hallucination risk; allow `vlm` for complex layout.
- OCR/table/formula toggles.
- Small-file no-token mode: may be offered only after an explicit user action; do not run `flash-extract` automatically on install or upload.

### Packaging And Token Bootstrap

V1.2 now stages the MinerU Open API client during Electron packaging instead of requiring users to install it manually. This only provides the executable; extraction still requires explicit workspace enablement plus a token.

Recommended behavior:

1. On startup or when a user uploads a PDF/image document, detect:
   - bundled `mineru-open-api`,
   - existing system `mineru-open-api`,
   - saved app token,
   - environment/config token.
2. If no token is found:
   - keep flash mode available for eligible files,
   - show a credential dialog when the user enables precision extraction or uploads a file that exceeds flash limits,
   - dialog title: "Enable MinerU precision extraction",
   - fields: token input, remember token checkbox, test token button,
   - link: https://mineru.net/apiManage/token,
   - secondary link: https://mineru.net/apiManage/docs.
3. If a token is saved:
   - store it in the app secure credential store, not project files,
   - mark MinerU precision extraction as ready in settings,
   - do a lightweight token check before the first paid/precision extraction.

Bundling note: the packaged app includes only the MinerU client/tool. It must never include a private API token.

### Tests

- CLI detection test with mocked `mineru-open-api version`.
- Token bootstrap test: missing token opens the MinerU token dialog only when precision extraction is needed.
- Extraction routing test: PDF + MinerU enabled sets `markdownPath` and `extractionManifestPath`.
- Fallback test: MinerU failure keeps original attachment and does not block send.
- Prompt test: processed PDF attachment includes `[Markdown version: ...]`.
- Project Memory test: citation index records source path, manifest path, page/block reference.
- Watermark cleanup test: repeated overlay text is suppressed from body Markdown and logged.

## Direction 4: Optional Search Foundation With AnySearch MCP

### Problem

Agent Pi needs a consistent search foundation for research, source verification, and document drafting. Relying on each model provider's browsing behavior makes results inconsistent and hard to audit.

### Proposed Product Behavior

- Show AnySearch MCP as a built-in recommended connector in settings, but keep it disabled until loaded by the user.
- Do not silently enable authenticated search without a user key.
- When the user clicks "Load AnySearch MCP" and no key is configured, open a credential dialog.
- Dialog field: API key input. Saving writes to the app secure credential store.
- Dialog links:
  - Search API docs: https://www.anysearch.com/docs#search-api
  - API key console: https://anysearch.com/console/api-keys
- Skipping the key keeps the recommended connector disabled and unauthenticated. Do not add an anonymous fallback in V1.2.
- With a valid key, save it in secure credential storage and mark AnySearch ready. Do not enable it for new research/document sessions until the user explicitly turns it on for the workspace or current task.

### MCP Configuration

Prefer native Streamable HTTP when the app runtime supports it:

```json
{
  "mcpServers": {
    "anysearch": {
      "type": "streamable-http",
      "url": "https://api.anysearch.com/mcp",
      "headers": {
        "Authorization": "Bearer ${ANYSEARCH_API_KEY}"
      }
    }
  }
}
```

For external clients that only support stdio, export a proxy config instead of making it the internal default:

```json
{
  "mcpServers": {
    "anysearch": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "https://api.anysearch.com/mcp",
        "--header",
        "Authorization: Bearer ${ANYSEARCH_API_KEY}"
      ]
    }
  }
}
```

V1.2 should prefer the native Streamable HTTP path inside Agent Pi. The stdio proxy path is useful for compatibility exports, but it adds an unnecessary local Node process when the app can call the remote MCP endpoint directly.

### Agent Routing

- Current external facts, market data, source checks, and web research should route through AnySearch first when enabled.
- If the user asks to avoid external search, do not call AnySearch.
- Project-local questions should use local workspace/project memory first, then search only if the prompt requires external verification.
- Quota/auth failures should surface connector status and ask for a key. Invalid/expired keys should not silently downgrade to another search mode.

### Tests

- Settings test: no AnySearch key opens the API key dialog on "Load AnySearch MCP".
- Skip test: skipping the key keeps AnySearch disabled and unauthenticated.
- Credential test: saved key is stored in secure credential storage and not written to project files.
- Config test: enabled connector uses `https://api.anysearch.com/mcp`.
- Header test: authenticated calls include `Authorization: Bearer ${ANYSEARCH_API_KEY}`.
- Routing test: research tasks can use AnySearch, local-only tasks do not.
- Auth failure test: invalid key shows an error and does not silently downgrade to another search mode.

## Key Risks

- MinerU JSON schema may differ by version. Mitigation: normalize through an adapter and store raw JSON separately.
- Large PDFs can slow foreground attachment storage. Mitigation: run extraction as background job and update attachment metadata when complete.
- OCR cleanup can remove meaningful legal marks. Mitigation: non-destructive derivatives, audit log, conservative defaults.
- Selection rewrite can overwrite user edits. Mitigation: hash selected text, keep Tiptap undo, save with mtime check.
- Export actions on non-Markdown files can confuse users. Mitigation: only show export when a Markdown source or derivative exists.
- AnySearch can look ready before credentials exist. Mitigation: keep the source disabled/needs_auth until a key is saved and the user explicitly enables it.
- API tokens can leak through project config or logs. Mitigation: use the app secure credential store and redact connector diagnostics.

## Recommendation

V1.2 is technically feasible and should be implemented in the order above.

The highest leverage path is:

1. Normalize file preview actions.
2. Add AI selection rewrite for Markdown outputs.
3. Add MinerU extraction as an optional provider that populates `markdownPath` and Project Memory citation indexes.
4. Add first-run setup for bundled MinerU and preloaded AnySearch MCP search so non-technical users can configure tokens from dialogs instead of editing environment variables, while both integrations remain off until explicitly enabled.

This sequence improves immediate usability first, then adds the deeper document-intelligence layer without destabilizing existing attachment and conversation flows.

# Agent Pi 企业知识库增强方案（暂不实施）

> 状态：仅作为未来研究与决策备忘，不代表已批准开发，不包含任何代码实现。

## 1. 目标

Agent Pi 已经具备全局知识库注册表、入库文件托管副本、单文件 file-memory MCP，以及按工作目录隔离的项目记忆。未来只有在现有单文件词法检索出现可测量的规模或质量瓶颈时，才考虑增加可重建的全文/向量检索索引，而不是替换现有机制。

必须坚持三个原则：

1. 原始文件、manifest、引用记录和项目记忆 JSONL 始终是权威数据。
2. 全文或向量数据库只是可删除、可重建的派生索引。
3. 全局企业知识和项目本地记忆必须显式分离。

## 2. 推荐方向

Zvec 可作为未来候选的嵌入式检索后端。它可以在不部署独立数据库服务的情况下提供全文、稠密/稀疏向量、标量过滤和本地持久化，但只有通过检索适配层、功能开关和离线评测后才可试点。

| 应用区域 | 建议定位 |
|---|---|
| 企业知识库 | 首个试点方向；在保留托管原文件的前提下提供跨文件混合检索 |
| 项目记忆 | 每个工作目录使用物理独立的索引 |
| 会话记忆 | 只索引提炼后的约束、决策、已验证事实、未决缺口和验收产物 |
| 原始对话和工具日志 | 默认不索引 |
| 权威存储 | 继续使用现有文件、registry、manifest、引用和 JSONL |

## 3. 隔离模型

### 3.1 全局企业知识库

可选的全局索引应放在 Agent Pi 应用数据目录。每个会话只能查询用户明确选择的知识库分类或条目；来源选择、权限范围、文档版本和分类必须成为强制查询过滤条件，不能只依赖提示词约束。

### 3.2 项目记忆

优先为每个工作目录建立物理独立索引，例如：

```text
<working-directory>/.agent-pi/brain/index/zvec/
```

索引记录同时保存规范化项目标识。物理隔离加项目标识校验，比把全部项目放入一个总库、只依赖 metadata 过滤更安全。

应用不得自动索引整个工作目录。允许进入项目记忆的内容仅包括：用户明确选择的来源、已验收正式产物、用户主动提升的过程产物、经验证的 Goal Audit 结论、已确认决策和可追溯提取引用。

### 3.3 会话记忆

短期执行状态继续保存在任务板和 progress ledger。只有具有跨会话价值的信息才提升到项目记忆，并保留可信状态、出处、版本及保留原因。

## 4. 检索模型

专业文档场景不能只依赖向量相似度，推荐采用混合检索：

1. 首先执行项目、已选来源、知识集合、权限和版本硬边界过滤。
2. 使用全文检索召回条款号、BOQ 编码、WBS、名称和精确术语。
3. 使用稠密向量召回语义相关和改写表达。
4. 对专业术语可选用稀疏向量。
5. 按相关度、可信度、来源质量、时效和版本融合重排。
6. 返回带文件、页码、条款、行号、工作表、单元格或 bbox 的引用级证据。

检索结果应形成 evidence package，而不是没有限定条件的文本片段。

## 5. 建议记录字段

```text
scope_type, scope_id, collection_id
document_id, document_version, chunk_id
title, content, language
source_path, page, clause, start_line, end_line, sheet, cell_range, bbox
memory_type, trust_level, created_at
content_hash, embedding_model, embedding_version
superseded_by, deleted_at
```

Embedding 生成必须与数据库解耦，并明确记录模型、版本、维度、语言覆盖和重建要求。

## 6. 运行边界

Agent Pi 包含 Electron 主进程和多个智能体/服务子进程。如果采用 Zvec 的单写者模型，应由主进程中的 `MemoryIndexService` 独占写入；其他智能体通过 IPC 或统一 MCP 服务提交索引和查询请求，不允许各自打开写入实例。

现有 file-memory MCP 继续作为兼容和精确读取后端。未来统一知识 MCP 可考虑暴露：

- `knowledge_search`
- `knowledge_read`
- `knowledge_manifest`
- `knowledge_citation`
- `project_memory_search`

## 7. 主要风险

- Zvec 仍是 1.0 以前的依赖，需要升级兼容和崩溃恢复验证。
- 其官方平台覆盖与 Agent Pi 全部发行目标并不完全一致，尤其需要处理 macOS x64 回退。
- Node/Electron 原生模块的 ABI、打包、签名和应用升级需要独立验证。
- 检索质量仍取决于分块、Embedding、来源边界、版本治理和记忆准入规则。
- 向量数据库不能自动决定哪些内容值得记忆，也不能弱化用户显式选择来源的规则。

## 8. 实施前评测

任何实施决策前先运行隔离评测：

- 对比当前词法检索、Zvec 全文检索、纯向量和混合检索。
- 覆盖中文、英文、中英混合、条款号、BOQ 编码、同义表达、跨文件、重复版本和过期来源查询。
- 测量 Recall@10、引用定位正确率、跨项目泄漏、P95 延迟、内存、索引体积、冷启动、崩溃恢复和并发智能体行为。
- 验证 Windows x64、Linux、macOS ARM64，以及不受支持目标的回退路径。
- 跨项目和未选择来源的泄漏数量必须为零。

## 9. 可能阶段

1. **仅评测：** 设计检索适配层并建立离线基准，不改变用户行为。
2. **企业知识库试点：** 可选跨文件混合索引，双路检索对比并保留现有 MCP 回退。
3. **项目记忆试点：** 为紧凑、可信的项目记忆建立项目独立索引。
4. **生命周期治理：** 增加去重、替代、过期、删除、用户检查和完整重建。

## 10. 当前决定

当前不实施。只有当检索失败率、语料规模或单文件 MCP 管理成本达到可测量阈值时，再重新评估引入该依赖所增加的复杂性是否值得。

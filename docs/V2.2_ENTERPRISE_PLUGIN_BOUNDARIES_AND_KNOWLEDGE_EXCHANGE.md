# Agent Pi Enterprise Plugin Boundaries and Knowledge Exchange

Status: Architecture boundary for V2.2 and later enterprise plugins.

## 1. Independent Product Plugins

Agent Pi will develop three independent enterprise plugins:

| Plugin | System of record | Required startup input | Optional upstream evidence |
| --- | --- | --- | --- |
| Tender Intelligence | Tender Workspace | User-selected tender sources | Enterprise knowledge items |
| Project Delivery Controls | Delivery Workspace | User-owned contract, scope, plan, cost, organization, or progress records | Tender snapshot and enterprise knowledge items |
| Resource Investment Intelligence | Investment Workspace | User-owned asset, geology, market, technical, financial, legal, ESG, or governance records | Tender, delivery, and enterprise knowledge items |

Independence means:

1. each plugin has its own schema, persistence root, revisions, state machine, audit results, Skill,
   tool adapter, regression fixtures, and UI route;
2. one plugin can be installed, initialized, used, archived, and upgraded without another plugin;
3. no plugin reads or writes another plugin's private store;
4. missing tender data never blocks Project Delivery Controls;
5. missing delivery data never blocks Resource Investment Intelligence;
6. a model may propose a cross-plugin mapping, but only deterministic validation and explicit user
   confirmation may persist it.

## 2. Persistence Boundaries

```text
<working-directory>/.agent-pi/business/
  tender/<tender-project-id>/
  delivery/<delivery-project-id>/
  investment/<investment-project-id>/
```

The Enterprise Knowledge Base remains application-global and user-managed. Business workspaces store
only references to selected knowledge items and local verification results.

## 3. Knowledge Exchange Contract

Cross-plugin exchange uses a small immutable manifest:

```ts
export type EnterprisePluginId = 'tender' | 'delivery' | 'investment';

export type KnowledgeEvidenceRelation =
  | 'derived_from'
  | 'corroborates'
  | 'contradicts'
  | 'supersedes';

export interface EnterpriseKnowledgePublication {
  schemaVersion: 1;
  publicationId: string;
  producerPlugin: EnterprisePluginId;
  producerWorkspaceId: string;
  producerRevision: number;
  artifactType: string;
  title: string;
  managedArtifactPath: string;
  originalArtifactPath?: string;
  contentSha256: string;
  sourceLocators: Array<{
    sourceId: string;
    page?: number;
    sheet?: string;
    clause?: string;
    cell?: string;
    excerpt?: string;
  }>;
  approvalState: 'draft' | 'approved' | 'withdrawn';
  publishedAt: string;
  publishedBy: string;
}

export interface EnterpriseKnowledgeUse {
  publicationId: string;
  expectedSha256: string;
  consumerPlugin: EnterprisePluginId;
  consumerWorkspaceId: string;
  relation: KnowledgeEvidenceRelation;
  localEntityIds: string[];
  verificationState: 'unverified' | 'corroborated' | 'conflicted' | 'stale';
  verifiedAt?: string;
  note?: string;
}
```

The manifest is metadata, not a second business model. Domain records continue to use their own
typed locators and gates.

## 4. Publish and Consume Flow

### Publish

1. The user selects an approved artifact in a plugin workspace.
2. Agent Pi computes the content hash and captures current plugin/workspace revisions.
3. The user selects a knowledge-base folder and confirms publication.
4. Agent Pi copies the artifact into managed knowledge-base storage and writes the publication
   manifest next to the indexed file.
5. Withdrawal marks the publication withdrawn; it does not delete consuming audit history.

### Consume

1. The user loads selected knowledge items into the target workspace or session.
2. The target plugin records an `EnterpriseKnowledgeUse` reference.
3. The plugin maps claims to its own entities and runs its own deterministic validation.
4. Conflicting evidence creates a visible conflict; it never resolves by last-write-wins.
5. A hash or producer revision change marks the reference stale and requires explicit refresh.

## 5. Knowledge Is Evidence, Not Authority

- An approved tender methodology can support a delivery work package, but it cannot create an
  approved implementation baseline by itself.
- Actual delivery productivity can corroborate or contradict a future tender rate assumption, but
  it cannot silently overwrite the tender estimate.
- Investment assumptions can cite delivery cost history, but NPV, IRR, resource, reserve, valuation,
  and approval gates remain investment-domain decisions.
- Knowledge-base search results remain candidate evidence until the consuming plugin records an
  exact item, revision, source locator, and verification result.

## 6. MVP Scope

The first knowledge-exchange increment reuses the existing managed file-memory knowledge base:

1. publish approved Markdown, JSON, CSV, and report artifacts with a sidecar manifest;
2. load selected knowledge items through the existing knowledge-base selector;
3. persist publication ID, hash, producer revision, and relation in the consuming workspace;
4. warn on withdrawn, missing, hash-mismatched, or stale items;
5. show cross-plugin evidence and conflicts in audit output.

The implementation should extend, not replace, the existing managed-copy flow in
`packages/server-core/src/handlers/rpc/knowledge-base-file-import.ts` and
`packages/server-core/src/handlers/rpc/sources.ts`. The managed artifact path is authoritative after
publication; the original path is provenance metadata only.

Automatic synchronization, a shared vector database, team collaboration, and background cross-project
reasoning are deferred. They would weaken plugin isolation before the evidence contract is proven.

## 7. Acceptance Gates

- Project Delivery Controls initializes successfully with no Tender Workspace present.
- An optional tender import creates a frozen snapshot and never changes after tender edits.
- A plugin cannot mutate another plugin's files through knowledge publication or consumption.
- A changed knowledge artifact is detected by hash mismatch.
- Conflicting publications remain visible and cannot both be marked corroborated for the same claim.
- Deleting a source conversation or project output does not delete the managed knowledge copy.
- A knowledge item alone cannot satisfy a tender, delivery, or investment completion gate without
  domain validation.

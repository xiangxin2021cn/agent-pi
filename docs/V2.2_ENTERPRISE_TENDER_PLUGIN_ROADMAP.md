# Agent Pi V2.2 Enterprise Tender Plugin Roadmap

Status: Tender Intelligence Core is the required foundation for tender packs only. Downstream tender packs must consume stable workspace IDs and must not independently rescan the project directory or reconstruct tender facts from chat.

## Shared Contract

Every tender pack consumes `project.id`, registered `document.id` values, `requirement.id`, `criterion.id`, `deliverable.id`, and `response.id`. New domain entities must preserve source locators and expose deterministic validation. Model judgment may propose mappings; only validated mappings enter the system of record.

## Pack Boundaries

Each pack must provide:

1. a small versioned domain schema;
2. an application-owned persistence and validation tool;
3. a bounded Skill that uses selected sources only;
4. synthetic complete and incomplete regression fixtures;
5. a Goal Audit adapter only for explicit completion claims;
6. a dense operational UI only after model behavior is stable.

Packs may request human confirmation when source precedence, engineering interpretation, commercial assumptions, or approval authority is ambiguous. They must not turn unresolved assumptions into unconditional conclusions.

## Product Plugin Boundaries

The remaining six entries above complete the Tender Intelligence plugin. They do not include project
implementation or investment work.

- **Project Delivery Controls** is a separate plugin with its own project store. It can initialize
  entirely from user-owned implementation data. A tender workspace is optional and, when used, is
  imported as a one-time versioned mapping snapshot rather than a live dependency.
- **Resource Investment Intelligence** is a separate plugin with its own asset, study, assumption,
  valuation, governance, and decision records. It must not infer resources, reserves, economics, or
  approvals from tender or delivery records.
- **Enterprise Knowledge Base** is the only shared evidence exchange. Publishing and loading are
  explicit user actions. Consumers receive immutable content hashes, source locators, producer
  module metadata, and revision state; they never receive write access to the producer's store.

Cross-plugin knowledge can corroborate or challenge conclusions, but it cannot silently satisfy a
domain gate. Each consuming plugin must validate the evidence against its own schema and acceptance
rules.

## Next Implementation Target

Implement Evaluation Strategy first because it uses the existing requirements and criteria without introducing quantity, scheduling, or pricing engines. Its first UI should be a compact register with source, criterion method, weight or threshold, response owner, evidence status, and coverage state. BOQ reconciliation follows only after this register is stable.
